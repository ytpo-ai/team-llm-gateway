# 2026-11-07 工作日志

## 渠道健康熔断与被动信号强化（PROVIDER_USAGE_HEALTH）

昨日交付的渠道用量感知（PROVIDER_USAGE_SENSE）中，主动查询链路（`UpstreamAdapter.fetchUsage()` 无任何实现 + 通用 `usageEndpoint` 字段猜测）在多数 LLM 平台不可用，属鸡肋。本日砍掉主动查询，改为纯被动信号驱动的渠道健康模型，并补齐网络错误兜底 fallback。

**完成事项**

- 移除主动查询链路：删 `ProviderUsageService.fetchAndCache()` / `genericFetchUsage()` 及辅助方法、删 `POST /providers/:id/fetch-usage` 端点；Provider schema/DTO/service 移除 `usageEndpoint`；`UpstreamAdapter` 移除 `fetchUsage()` 与 `ProviderUsageSnapshot` 类型；ProviderUsage 移除 `quotaTotal/quotaUsed/quotaUnit`。
- ProviderUsage 改造为渠道健康模型：新增 `exhaustedUntil`（429 恢复时间）、`consecutiveFailures`、`cooldownUntil`（熔断冷却截止时间），替代旧 `isExhausted` 布尔语义。
- `markExhausted()` 升级：解析 `Retry-After` / `x-ratelimit-reset-*` 响应头推算恢复时间，缺省回落可配窗口（默认 60s），重复 429 按连续失败次数指数退避。
- 新增 `recordFailure()`：连续失败达阈值（默认 3）进入熔断冷却，指数退避 30s 基数、10min 封顶；新增 `recordSuccess()`：成功请求重置失败计数与不可用状态。
- 统一可用性判定 `getAvailability()` 替代旧 `isExhausted()`，`tryCandidate()` 跳过限流中/冷却中渠道并记日志。
- 转发层四入口统一接线：429 → markExhausted（带响应头）；5xx/408 → recordFailure；**网络异常新增 try/catch 兜底**（fetch 抛错原先直接 500 无 fallback）→ recordFailure + 切换下一候选；成功 → recordSuccess。
- 新增配置 `providerHealth.failureThreshold` / `cooldownBaseMs` / `cooldownMaxMs` / `rateLimitCooldownMs`（configuration.ts + `.env.example`）。
- 前端：渠道表单移除「用量查询端点」字段、移除 🔍 探测按钮与 `fetchProviderUsage` API；「用量探测」列改造为「健康状态」列（限流中-黄/冷却中-红/正常-绿含速率余量/未探测-灰）。
- 测试：新增 `provider-usage.service.spec.ts`（13 例：可用性判定/429 恢复窗口解析/退避/熔断/成功重置/响应头提取）；`proxy.service.spec.ts` 新增 4 例（网络错误 fallback、429 带响应头、5xx+成功信号、冷却渠道跳过）。
- 验证：后端 lint / typecheck / test（236 passed）；前端 typecheck / lint / build 全通过。

## 1. 项目定位

### 1.1 业务本质

**我们是「服务商」**，不是内部工具。向小型产研/办公团队提供一站式 AI 接入服务，通过提供服务盈利。

### 1.2 服务内容（两大块）

1. **LLM 中转站**：模型流量中转分发、模型接入、账号流量池与路由、Token 成本监控（客户级）。
2. **团队使用优化**：帮助客户团队接入模型、管理成员/密钥、控制 Token 成本、持续优化使用。

### 1.3 核心价值主张

- 帮助小型团队**快速接入**市面常用模型（含国内用户访问受限的 ClaudeCode / GPT / Gemini 等国外先进模型 + 国内常用模型）。
- 根据**模型能力和办公场景**给出一套**模型选用方案**，达到合理的 Token 成本控制与优化（这是相对参考项目的差异化点，见第 8 节）。
- 对成员模型访问与 Token 做合理限制，对 Token 使用做丰富可视化，持续优化团队 Token 使用。

### 1.4 商业模式（双轨）

| 形态 | 说明 |
|---|---|
| **软件交付** | Gateway（中转站）、Portal（团队接入平台）可作为独立软件交付/开源，对方自行部署运维 |
| **托管 SaaS** | 我们运营「超级 Portal」，向客户团队提供托管服务并计费 |

## 2. 产品矩阵（两条产品线、两个代码库）

| 产品线 | 代码库 | 交付形态 | 租户模型 | 上游 |
|---|---|---|---|---|
| **中转站线** | Gateway（Go / New API 内核） | 独立软件，**外包自运维** | 客户（个人/团队） | LLM 厂商 + 账号流量池 |
| **团队平台线** | Portal（TS/Nest） | ① 开源单团队版 ② 超级 Portal（我们运营 SaaS） | 单租户 ↔ 多租户 | LLM / 任意中转 / Gateway |

### 2.1 三个可独立交付的软件

| 组件 | 交付形态 | 谁来用/部署 | 职责本质 |
|---|---|---|---|
| **Gateway（中转站）** | 稳定软件，可外包 | 我们维护软件，合作方配置上游流量池并自行运维 | 模型接入 + 流量池 + 路由 + 客户级计量 |
| **Portal（团队接入平台）** | 独立开源 | 团队自部署，直连 LLM 或任意第三方中转 | 团队/成员/APIKey + 细粒度计量 + 选型建议 |
| **超级 Portal（SaaS）** | 我们运营 | 客户团队采购我们的服务 | 多租户版 Portal + 计费 + 服务商全局视角 |

### 2.2 Portal 与「超级 Portal」的关系

**是同一套代码的两种形态，不是两套系统：**

```
Portal 核心（TS/Nest）＝ 团队 → 成员(角色) → 多Key → 细粒度限制 + 计量 + 选型建议
   ├─ 开源单团队版：租户数 = 1，团队自助部署，只看自己
   └─ 超级 Portal（SaaS）：租户数 = N，我们运营，服务商角色看全局
```

**架构方向：Portal 核心从一开始就按「多租户」设计，单团队开源版只是「租户数=1 + 隐藏超级管理员」的特例**，开源版与 SaaS 版共享同一套代码。

## 3. 架构总览

```
┌────────────────────────────────────────────┐
│  Portal 核心（TS/Nest，多租户设计）          │
│   团队/成员/key/细粒度限制/计量/选型建议      │
├───────────────┬────────────────────────────┤
│ 开源单团队版   │ 超级 Portal（我们运营 SaaS） │
└───────┬───────┴────────────┬───────────────┘
        │  OpenAI 兼容（统一上游抽象）│
   ┌────┼──────────────┐     │
   ▼    ▼              ▼     ▼
 直连   Gateway        任意第三方中转
(OpenAI/Anthropic/...)
        │
        ▼
   Gateway 内核（New API，Go）
   ├─ 客户/令牌/渠道流量池/计费/客户级计量
   └─ 上游 LLM 厂商（含账号池）
```

**核心解耦原则**：Gateway 和「任意第三方中转」对 Portal 来说长得完全一样（都是 OpenAI 兼容接口 + 一个 key）。Portal 的上游抽象只需支持「OpenAI 兼容」这一种，**Gateway 不需要为 Portal 做任何特殊定制**。

## 4. 核心决策记录（ADR）

> 每条记录：背景 → 决策 → 理由 → 影响。出现分歧时以此为准。

### ADR-01：业务定位为「服务商」，而非内部工具

- **背景**：TARGET.md 同时出现「为小型团队提供服务」（B2B 多租户）与「客户系统面向我们自己」两种信号。
- **决策**：本质是服务商，向客户团队提供服务；团队管理平台与客户系统合并为同一套 SaaS，分不同角色登录。
- **理由**：服务商定位决定租户模型、计费模型、权限模型的整体走向，必须先行锚定。
- **影响**：后续所有计费、角色、多租户设计均以「服务商服务多个客户团队」为前提。

### ADR-02：产品矩阵为「两条产品线、两个代码库」

- **决策**：中转站线（Gateway，Go/New API 内核）与团队平台线（Portal，TS/Nest）相互独立，各自可独立交付。
- **理由**：Gateway 功能场景独立（部分团队只需要中转站），后期可外包给不同团队自运维；Portal 可独立开源，团队在未采购服务时也可自部署直连 LLM 或第三方中转。
- **影响**：两个代码库独立演进，通过 OpenAI 兼容接口对接，互不耦合。

### ADR-03：SaaS 形态为「超级 Portal」，而非「Portal + Gateway 组合」

- **决策**：我们运营的 SaaS = 管理多团队的「超级 Portal」（多租户版 Portal），Gateway 不构成 SaaS 的组成部分，仅是 SaaS 的可选上游之一。
- **理由**：Portal 与超级 Portal 是同一套代码的两种形态，多租户能力内建于 Portal 核心。
- **影响**：Portal 核心按多租户设计；开源单团队版是租户数=1 的特例。

### ADR-04：技术栈 = Go 引擎 + TS 业务，组件化/微服务化

- **决策**：
  - Gateway 数据面（协议翻译/路由/限流/客户级计量）：**Go**（复用 New API）。
  - Portal 业务面（团队/计费/选型/UI）：**TS/Nest**。
  - 核心功能组件化/微服务化，部分性能敏感模块允许使用不同语言组件。
- **理由**：团队技术栈偏好 Node/TS 与 Go；性能敏感路径用 Go（new-api 已验证），业务逻辑与前端统一用 TS/Nest。
- **影响**：组件间通过标准接口（OpenAI 兼容 + 管理 API / gRPC / 消息队列）通信。

### ADR-05：Go/TS 可充分实现 LiteLLM 核心能力，无需 Rust

- **背景**：LiteLLM 以 Python + Rust 编写，团队阅读 Python 有挑战，担心语言无法替代。
- **决策**：用 Go 或 TS 实现 LiteLLM 的核心能力（协议翻译/虚拟密钥/限流/路由/计量），语言上完全充分。
- **理由**：LiteLLM 核心能力本质是「HTTP + JSON 映射」+ 通用工程能力，无语言依赖。Rust 只是 LiteLLM 因 Python 性能差而引入的补救措施，非能力依赖。第三方基准（AIGatewayBench）显示 TS（Portkey 2.3ms p99）与 Go（Bifrost 4.5ms p99）网关开销均在个位数毫秒，均比 Python 版 LiteLLM（257.7ms）快 50~100 倍。
- **影响**：语言选型以团队偏好与工程生态为准，无需引入 Rust。

### ADR-06：计量分层——Gateway 客户级，Portal 团队细粒度

- **决策**：
  - **Gateway**：只需知道「是哪个客户 + 多少 token + 多少钱」，客户可拆分为多个 apikey。
  - **Portal**：团队 → 成员（不同角色）→ 多 key → 每个 key 细粒度设置 LLM 使用限制，需更细粒度计量。
- **理由**：Gateway 服务「中转站流量池」场景，粗粒度即可；Portal 服务「团队协作」场景，需精细到成员/key 级。
- **影响**：计量是两层都要有的基础能力，各自维护对应粒度的计量数据。

### ADR-07：Gateway 复用 New API 能力

- **决策**：Gateway 尽量复用现有 New API 的能力，作为现成中转站内核。
- **理由**：New API 的「用户/令牌/渠道池/计费/计量」模型与 Gateway 的中转站定位完全匹配；且 New API 单二进制 + SQLite + Docker 一条命令、运维最轻，契合「外包自运维」。
- **影响**：Gateway 基于 New API 改造（Go），改造边界（保留/裁剪）见待决事项 D-01。

### ADR-08：Gateway 外包自运维

- **决策**：Gateway 由合作方自行部署运维，我们负责提供稳定软件。
- **理由**：业务上我们希望聚焦软件与核心服务，中转站可复制交给不同团队运营。
- **影响**：Gateway 软件须具备「开箱即用、稳定、易运维、可独立交付」特性，进一步强化 ADR-07 的选型结论。

### ADR-09：Portal ↔ Gateway 的 key 衔接采用「方案 A」

- **背景**：Portal 与 Gateway 的 key 如何衔接存在两种方案。
- **决策（方案 A）**：Portal 在 Gateway 开一个「团队上游账号/key」，团队成员 key 由 Portal 自己签发；成员请求先到 Portal，Portal 用团队上游 key 转发到 Gateway。
- **理由**：Gateway 只看到「这个团队用了多少」（客户级计量成立），团队内部细粒度由 Portal 掌控；两种组件边界清晰，符合 ADR-06 计量分层。
- **影响**：Gateway 无需理解团队内部结构；Portal 负责成员级鉴权、细粒度限制与计量。

### ADR-10：计费模式采用「统一扣费引擎 + 可插拔额度来源」

- **决策**：保留足够多计费模式以方便业务扩展，抽象为可插拔计费模型：

```
额度来源（可插拔渠道）  →  额度账户   →  扣费引擎
────────────────────      ────────      ────────
充值/订阅/兑换码/          团队额度     按「模型倍率 × token」扣
月结账单/赠送额度/         成员额度     （含缓存计费/阶梯价）
```

- **理由**：避免维护 N 套并行计费代码；新增计费模式只需增加一个额度来源插件。
- **影响**：扣费引擎唯一（模型倍率 × token），额度来源可插拔，额度账户分团队级/成员级。

### ADR-11：Gateway 基于 New API 改造并接受开源（AGPLv3）

- **背景**：New API 采用 AGPLv3 + §7 附加署名条款，D-01 评估「重写 vs 改造」时发现授权合规是唯一重大风险。
- **决策**：Gateway 基于 New API 二次开发（改造而非重写），并**接受开源**，随同 AGPLv3 发布；仅做「裁剪过度设计模块 + 品牌化（遵守 §7 署名）+ 前端裁剪同步 + 部署固化」。
- **理由**：New API 与 Gateway 中转站定位高度重合，改造 1~2 人周 vs 重写 456K 行代码；接受开源与「可独立交付软件」(ADR-02/08) 兼容，并可长期跟随上游主线。
- **影响**：Gateway 随同开源并履行 §7 署名义务；D-01 裁剪清单见 `GATEWAY_NEWAPI_FEATURE_CUT.MD`。

### ADR-12：开发优先级——Portal 优先，Gateway 改造暂缓

- **背景**：D-01 评估结论为「基于 New API 改造」，但 New API 现状已满足中转站核心需求。
- **决策**：**暂不对 Gateway（New API）做任何改动**，`forks/new-api` 保持原样作为可直接部署的中转站内核；当前阶段集中资源开发 **Portal**，待 Portal 完成后再回头执行 New API 的裁剪与品牌化优化。
- **理由**：New API 开箱即可用，Gateway 改造的投入产出比低；Portal 是差异化价值所在（选型建议/团队细粒度计量/Token 优化），是产品护城河。
- **影响**：D-01 清单作为后续 Gateway 优化的参考存档，暂不执行；后续待决事项（D-02~D-05）全部聚焦 Portal。

### ADR-13：Gateway↔Proxy 关系——proxy 是首选上游，非必经

- **背景**：命名与历史措辞（`team-llm-proxy` 原 Gateway、`team-llm-gateway` 原 Portal）使「gateway 接入 proxy」产生歧义，仿佛 proxy 是 gateway 的唯一/必经上游。而原始需求讨论中明确：proxy 只是 gateway 的一个主流上游，gateway 可接入任何 LLM 官方或第三方服务。
- **决策**：
  - `team-llm-proxy` 是 `team-llm-gateway` 的**首选上游（默认走 proxy）**，但**可旁路**：gateway 可直连任意 OpenAI 兼容的 LLM 官方（OpenAI/Anthropic/DeepSeek…）或第三方中转。
  - 三者（直连官方 / 第三方中转 / 自有 proxy）对 gateway 而言**长得完全一样**（OpenAI 兼容接口 + 一个 key），proxy 无特殊地位、无专属定制接口。
  - proxy 因提供「账号流量池 + 路由 + 客户级计量」的增值能力而作为推荐默认上游；当团队自有上游账号或采用第三方中转时，可旁路 proxy。
- **理由**：原始需求讨论即表达「proxy 只是 gateway 的一个主流上游」；proxy 作为首选是因为其流量池/路由/计量的增值能力，但不应形成硬耦合，需保证 gateway 独立交付能力（ADR-02/08）。
- **影响**：
  - 与 ADR-03 一致并进一步明确：proxy 不构成 SaaS 的必需组件，是「首选但可旁路」的上游之一。
  - Portal 上游抽象仅需支持「OpenAI 兼容」一种（§3 核心解耦原则），proxy 无需为 Portal 做任何特殊定制。
  - 命名（`team-llm-gateway`/`team-llm-proxy`）保持不变，仅在文档层面明确关系、消除歧义。

## 5. 组件边界

### 5.1 Gateway（中转站）

**负责**：模型接入（国外 + 国内）、账号流量池与渠道路由、协议翻译、限流、**客户级计量**、客户计费。

**不负责**：团队/成员/角色的业务管理、细粒度计量、选型建议（这些归 Portal）。

### 5.2 Portal（团队接入平台）

**负责**：团队 → 成员（角色）→ 多 key 的层级管理、每个 key 的细粒度 LLM 使用限制、**团队级细粒度计量**、用量可视化、模型选型建议、计费定价（团队级）。

**上游**：统一「OpenAI 兼容」抽象，支持直连 LLM 官方 / 第三方中转 / 自有 `team-llm-proxy` 三类上游，三者无特殊地位。`team-llm-proxy` 作为**首选上游（默认走 proxy）**，但**可旁路**（见 ADR-13）。

**不负责**：上游账号流量池的配置与调度（直连时由团队自行配置；连 Gateway/第三方中转时由上游方负责）。

### 5.3 超级 Portal（SaaS）

**负责**：多租户管理、服务商全局视角（看多个团队的基础情况与模型使用情况）、客户团队角色的托管接入。

**不负责**：上游中转站运维（Gateway 外包，见 ADR-08）。

## 6. 技术选型

| 层 | 技术 | 说明 |
|---|---|---|
| Gateway 数据面 | Go | 复用 New API 内核，性能敏感路径 |
| Portal 业务面 | TypeScript / Nest.js | 团队/计费/选型/UI 统一 |
| Portal 前端 | React + TypeScript + Tailwind | 主应用 |
| 数据库 | MongoDB (Mongoose) | Portal 业务数据 |
| Gateway 存储 | New API 默认（SQLite 起步 / 生产 PG+MySQL+Redis） | 随 New API 改造方案确定 |
| 组件间接口 | OpenAI 兼容 API + 管理 API（/ gRPC / 消息队列） | 组件化/微服务化 |

## 7. 计量与计费模型

### 7.1 计量粒度对照

| 层级 | 对象 | 说明 |
|---|---|---|
| Gateway（客户级） | 客户 → 多个 apikey | 谁用了多少 token、花多少钱 |
| Portal（团队级） | 团队 → 成员(角色) → 多 key → 每 key 细粒度限制 | 精细到成员/key 的用量与限制 |

### 7.2 计费模型（可插拔）

- **扣费引擎**（唯一）：模型倍率 × token，含缓存计费、阶梯价。
- **额度来源**（可插拔）：充值、订阅、兑换码、月结账单、赠送额度……
- **额度账户**：团队级 / 成员级；服务商角色可全局看所有团队额度池。

## 8. 差异化能力：模型选型建议

- **定位**：根据「模型能力 + 办公场景」给出一套模型选用方案（该场景用哪个模型、是否开缓存、是否降级到更便宜模型等），实现 Token 成本优化。
- **相对参考项目的独特性**：New API / LiteLLM / Portkey 均**只有路由与计费，没有主动的选型建议**。这是本项目相对三者的核心差异化能力，需单独展开设计（见待决事项 D-02）。

## 9. 参考项目功能定位

| 参考项目 | 在本项目中的位置 |
|---|---|
| **New API** | Gateway 内核（中转站/计费/团队/密钥能力），复用改造 |
| **LiteLLM** | 引擎层参考（统一接入、协议翻译、路由、预算、可观测的设计） |
| **Portkey** | 基本放弃（护栏/高可靠路由对办公场景过度设计；但其 TS 实现可作语言可行性佐证） |

> 详见 `docs/technical/LLM_API_GATEWAY_COMPARISON.MD`。
